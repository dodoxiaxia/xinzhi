# 首屏性能拆分与体积预算说明

公开站把原来单一的 `public.js` 拆成“首屏同步包 + 延迟数据分片 + 按需存档”，减少首屏加载和解析耗时；功能与本地开发视图保持一致。

## 一、首屏同步加载内容（第一层）

`public/index.html` 在首屏只同步引用带 12 位内容哈希的样式表和首屏脚本：

- `index.html`：页面骨架与主题初始化内联脚本。`_headers` 设为 `public, max-age=0, must-revalidate`（与 `/`、`demo-reading.html` 相同）。
- `assets/style.<哈希>.css`：全站样式（与 `style.css` 内容一致）。
- `assets/app.<哈希>.js`：按顺序包含三部分：
  1. `window.XINZHI_PARTS`：延迟分片清单（`v: 1`，按优先级列出各 `data-*` 文件路径）与 `window.RADAR_SRC`（按需雷达存档路径）。
  2. 首屏最小数据全局变量（由 `scripts/public_split.py` 的 `select_first_screen` 与 `split_parts` 裁出）：
     - `CURATED`：全部已核对导读条目。
     - `CONTENT_STATUS`：版本与内容更新时间状态。
     - `JOURNAL_METRICS`：期刊指标表。
     - `FEEDS`：只保留带 `autoPick` 或 `weeklyPick` 的候选条目，外加 `order: {total, at}` 记录原长度与下标，保证每日精选与近7天榜立即可用。
     - `LIBRARY` 与 `SOURCE_HEALTH`：仅保留时间戳与空列表占位，并带 `deferred: true`。
     - `QUICKLOOKS`：仅保留最新精选日且属于上述 `FEEDS` 子集的条目。
     - `PREGENERATED`：仅保留当前 `WEEKLY_BOARD` 条目中卡片首屏展示所需的 `quicklook` 字段；`translation`、`study`、`meta` 等阅读面板详情字段拆入延迟分片 `pregenerated`。
  3. 前端脚本代码：`journal-metrics.js`、`citation-export.js`、`journal-tiers.js`、`app.js`。

`assets/` 和 `shards/` 下带内容哈希的文件均由 `_headers` 设为 `public, max-age=31536000, immutable`。

## 二、延迟与按需加载内容（第二层）

- **延迟数据分片（`assets/data-<名称>.<哈希>.js`）**：按 `PART_ORDER` 依次为 `feeds`、`library`、`quicklooks`、`radar`、`pregenerated`、`readings`、`health`、`board`。每个文件调用 `window.XINZHI_PART("<名称>", <JSON 载荷>)`，把剩余候选条目、完整公开文献库（含 `pdfIds`）、其余 AI 速览、近 21 天（`RADAR_INLINE_DAYS`）雷达行、其余预生成内容、`DEEP_READINGS` 目录、信源健康详情和 `WEEKLY_BOARD` 合并回页面内存状态。
- **365 天雷达存档（`assets/radar.<哈希>.js`）**：存放 21 天前的 `window.RADAR_ARCHIVE`，仅在切换到 30/90/365 天视图或按精确 DOI 检索时由 `loadRadarArchive()` 按需加载。
- **全文精读正文分片（`shards/readings-年-月.<哈希>.js`）**：按 `publishedOn` 月份拆分，只在打开该月某篇全文精读时请求。
- **本地开发目录不变**：仓库根目录的 `index.html` 直接引用 `data/*.js`，没有 `window.XINZHI_PARTS`，不走延迟加载逻辑。离线脚本和检查工具通过 `scripts/public_bundle.py` / `scripts/public_bundle.cjs` 读取并还原完整全局变量。

## 三、如何新增一个全局变量

新增构建期注入的全局变量前，先判断它是否参与首屏默认视图渲染（“每日精选”最新一日与页面基本框架）：

1. **首屏不需要（推荐默认做法）**：
   - 在 `scripts/public_split.py` 的 `PART_ORDER` 与 `split_parts()` 中新增一个延迟分片（或并入已有相近分片），不要直接塞进 `first`。
   - 在 `src/app/*.js`（然后运行 `python3 scripts/build_sources.py` 更新 `app.js`）以及 `scripts/public_bundle.py`、`scripts/public_bundle.cjs` 中加入该分片的合并处理；在分片未到达前，前端读取该变量时须有安全的空默认值。
2. **首屏确实需要**：
   - 放进 `split_parts()` 返回的 `first` 中，并尽量只投影首屏真正用到的字段或子集（参考 `select_first_screen`），避免把整库或全量摘要带入第一层。
   - 跑一次构建和预算检查，确认没有超过首屏体积预算。

## 四、首屏体积预算常量与调整方式

首屏预算检查的纯函数位于 `scripts/public_split.py`，由 `scripts/build_public.py` 在写出 `public/` 前自动执行，也可通过 `python3 scripts/check_first_screen_budget.py [public_dir]` 单独复测。

- 测量对象：`index.html` 以及它同步引用的样式表和首屏脚本（不统计 `async`/`defer` 资源和延迟分片）。
- 压缩口径：固定使用 `gzip` 9 级（`mtime=0`）和 `brotli` 11 级；运行环境缺少 `brotli` 模块时，只测量 `gzip` 并打印跳过提示，构建仍继续。
- 三个模块常量（`scripts/public_split.py`）：
  - `FIRST_SCREEN_DATA_BUDGET_BR = 100_000`：首屏脚本中代码前各 `window.NAME=...;` 语句各自 `brotli(11)` 字节数之和的上限（本分支按十进制 100 KB 取保守上限 100,000 字节，非原规格书原文；对应 `gzip(9)` 上限为 125,000 字节）。
  - `FIRST_SCREEN_TOTAL_BUDGET_BR = 225 * 1024`：首屏关键文件（`index.html` + 样式表 + 首屏脚本）`brotli(11)` 总字节数上限（225 KiB，为前端脚本与样式保留单独余量）。
  - `FIRST_SCREEN_GZIP_TO_BR_RATIO = 1.25`：`gzip(9)` 上限等于对应 `brotli` 上限乘以该系数（数据 `gzip` 上限保持 125,000 字节不放宽）。同时对照 `gzip` 与 `brotli` 两个上限，取更严格的一侧；任一超限都会抛出 `ValueError` 并阻止写出 `public/`。
  - 若运行环境未安装 `brotli` 模块，仅执行对应 `gzip(9)` 上限检查并打印提示；发布前须在带 `brotli` 的环境（如 CI）同时核验两项上限。

### 如何审慎上调预算

1. 超限后应**优先把多余数据或大字段迁入 `assets/data-*.js` 延迟分片**，不要直接放宽预算。
2. 只有当确实增加了首屏必需功能（例如核心交互脚本或样式的合理增长），且已核实 `first` 中没有全量列表或大块冗余字段渗入后，才可以手动修改 `scripts/public_split.py` 中的预算常量。
3. 上调时必须以实测的 `raw / gzip(9) / brotli(11)` 为依据，保留约 10% 余量并在提交说明里写明增量来源；**禁止**根据 `state` 里的条目数推算或硬编码预算。
