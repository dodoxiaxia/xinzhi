## 推荐的第一阶段

公开阅读版先采用静态托管；当前已生成 `public/`，只有 5 个文件，没有模型密钥、索引本地路径或内部共读记录。

可用 Cloudflare Pages 托管公开文件并绑定子域名。官方文档明确支持 DNS 继续由原服务商管理：先在 Pages 添加自定义域名，再在原 DNS 增加指向项目 `pages.dev` 地址的 CNAME，无需仅为子域名迁移整个域名的 NS。

来源：https://developers.cloudflare.com/pages/configuration/custom-domains/ （本轮已查阅）

内部记录的低维护起点是 Google Workspace 指定成员共享的 Docs/Drive：公开网站只放入口，真正的访问限制由 Workspace 文件权限执行。不要使用“知道链接的任何人”，也不要把内部数据打包进公开网站后靠 JavaScript 隐藏。

如果需要网站内多人编辑、审核和成刊，则新增内部应用与数据库，采用 Google 身份认证，并按明确成员或群组授权。Cloudflare Access 可对接 Google Workspace 身份提供者，但这不等于已经完成应用、域名和后端鉴权配置。内部自定义域名的代理/DNS要求应在选择产品后单独确认，不假定公开站 CNAME 配好后内部鉴权便自动生效。

来源：https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/google-workspace/ （本轮已查阅）

## 域名与邮箱

`@dryz.info` 是邮箱地址的域名部分；`learn.dryz.info` 是网站主机名，二者可以共存。Google Workspace 邮件服务不直接等于网站托管。

本轮本地 DNS 查询返回 `ns-cloud-a1/a2/a3/a4.googledomains.com` 和 MX `1 smtp.google.com`。这支持邮箱由 Google 接收的现状，但不证明当前注册商或后台账号属于哪个平台。当前网络对子域名 A 查询返回了 198.18.0.76，属于保留地址范围，不能据此断言子域名已被占用或已部署。部署前以实际 DNS 管理后台记录为准。

拟变更清单：

| 类型 | 名称 | 值 | 处理 |
|---|---|---|---|
| CNAME | learn | 托管项目实际提供的地址 | 确定项目与核对原记录后新增 |
| MX | 现有邮件记录 | 原值 | 保留 |
| TXT | SPF / DKIM / DMARC / 验证记录 | 原值 | 保留 |
| NS | 当前权威服务器 | 原值 | 静态子域名方案不要求修改 |

## 上线执行顺序

1. 确认站名、子域名、DNS 管理平台、托管账号，以及公开内容是否使用本次预览。
2. 创建托管项目，仅上传发布清单里的公开文件。先检查临时预览地址。
3. 在托管平台关联 `learn.dryz.info`，再新增精确 DNS 记录，等待证书与解析就绪。
4. 建立内部记录空间并配置指定成员权限。若做内部网站，需要验证数据接口权限，不只验证登录页。
5. 匿名访问可读公开内容；未授权账号不能访问内部记录；授权账号可访问。检查备用地址、预览地址、直接数据链接，防止绕过访问控制。
6. 从科室实际电脑/手机网络测试加载、期刊链接与 Google 登录可达性；另验收原邮箱收发没有变化。
