# 网站运营与发布（v13.6）

执行端是 GitHub Actions，公开站点是 Cloudflare Pages `dryz-xinzhi` / https://learn.dryz.info/。`main` 保存代码和人工核对稿，私有 `state` 保存抓取数据、摘要缓存和最近成功发布的六文件。Macmini 是私有文献归档目标，网站发布不依赖它运行。AI- 原文下载与归档是另一条流程。

## 更新频率与内容边界

| 工作 | 频率（北京时间） | 完成标准 |
|---|---|---|
| RSS/PubMed 查新、当前源健康、规则精选 | 约每 4 小时（外部 :07 每 2 小时派发，gate 限最短间隔 170 分钟；GitHub cron :37 每 4 小时兜底） | 本轮获取状态、近 14 天候选、内容变更时发布 |
| 365 天存档、摘要补全、标题翻译、AI 速览 | 每天 04:47 | 总时间预算内执行；结果和跳过原因留报告 |
| 代码、页面、人工稿发布 | main 相关路径更新时 | 轻量查新与构建通过门槛并由 Pages 接受 |
| 摘要核对导读 | 新稿完成来源核对后 | 证据范围、来源 URL、published 日期；published=false 不公开 |
| AI 全文精读 | 每天 04:47 完整刷新，默认目标 8 篇，定时轻量刷新补足 | 公开全文身份、引句与数字核对通过后自动更新；明确未经人工审核，显示实际完成篇数；见 [每日全文精读](每日全文精读.md) |
| 人工全文精读 | 完成全文审查后按期发布 | 与 AI 精读分开，未完成显示尚未发布，不把旧期改日期 |

自动聚合、规则精选、AI 速览不等于人工核对或全文精读。公开文献库是既有 1,219 条题录范围；私有 AI- 索引增长不自动扩大公开范围。页面分别展示查新、导读和速览时间。

## 唯一发布入口

`.github/workflows/daily.yml` 保留已有两条 GitHub cron，不新建第三条调度。2026-10-10 起两条 cron 改到 :47 / :37（原 :17 / :07）：GitHub 官方说明整点前后高负载时定时任务会被延迟或丢弃，实测 2 小时快刷常间隔 4–6 小时、05:17 完整刷新曾晚 3.5 小时。手动 full/fast 均可直接运行。2026-10-10 起不再忽略 fast dispatch：已部署的旧 Cloudflare Cron Worker 每 2 小时 :07 准时派发 mode=fast，而同日 GitHub cron 9 小时以上未触发，它成为唯一准时的定时源；GitHub cron 保留作后备，并发组让重叠运行排队，无内容变化的快刷不发布。若要停用旧 Cron，须先确认 GitHub 定时恢复准时。完整刷新（付费：存档、补摘要、标题 60 批、AI 速览、全文精读、周预计算）按北京日期每天最多一次：定时/外部派发的快刷在 05:00 后若发现当天尚无成功的完整刷新，自动升级为完整刷新；当天已完成后，迟到的 04:47 定时完整刷新自动降为快刷。依据 `data/full-refresh-marker.json`（随 state 保存，仅在发布成功后推进）。手动 full 与代码推送不受影响。

2026-10-11 起（站点负责人决定）定时快刷放宽为约 3–4 小时一次：`daily.yml` 先运行一个只需几秒的 `gate` 任务（`scripts/fast_refresh_gate.py`），若上次成功的定时或完整刷新（`data/timed-refresh-marker.json`；代码推送触发的发布不调用模型，不计入）开始不足 170 分钟（仓库变量 `XINZHI_FAST_MIN_INTERVAL_MINUTES` 可调）则跳过这次定时快刷；当天完整刷新尚未完成时从不跳过；读不到上次记录时照常运行。外部每 2 小时派发因此实际约每 4 小时刷新一次。人工 fast 勾选 `force` 可跳过间隔限制；推送和 full 不经过限制。

固定 state 恢复 → RSS/PubMed → 合并 → 轻量精选；每天和人工 full 再做存档/补摘要/翻译/速览 → 白名单构建 → 门槛 → Pages → 成功后才写 state。main 源码更新使用 fast，避免小改动重复调用模型；推送触发的 fast 不调用模型或大存档，定时 fast 做一次有界中文标题翻译（≤30 条，精选优先）、最多 8 篇 AI 速览、周榜缺项补算，并补足当天未达标的全文精读；推送触发的 fast 只复用缓存。六个公开文件都进入内容比较；刷新时间变化不重新发布。full 总预算 110 分钟（存档补全最多用到只剩 60 分钟，其余留给模型步骤）、fast 40 分钟；Actions 硬上限 150 分钟。付费步骤通过 `XINZHI_STEP_DEADLINE` 得知本步时限，临近时不再发起新请求。可选步骤失败/超时/预算跳过如实记录。

public 必须恰好 index.html、public.js、radar.js、feed.xml、style.css、icon.svg、_headers、_worker.js（v14.4 起 radar.js 承载 21 天前的雷达存档，按需加载；feed.xml 为近 7 天每日精选 RSS，可在阅读器或群机器人订阅 https://learn.dryz.info/feed.xml）；雷达至少 300、文献库至少 1,000。摘要缓存缺失、既有导读丢失、公开私有路径或多余文件均停止构建。AI 单篇不通过证据校验则跳过，合法输出可保留；模型鉴权/限流/传输故障停止后续请求并保留旧缓存。诊断只含白名单元数据，不存响应或凭据。

## 定期运维和故障处理

v13.6 公开摘要研究结构/逐篇对照沿用现有 Pages KV 与模型配置，不新建调度。每次实际部署前执行 Worker、阅读逻辑、研究服务及 UI 的离线 Node 测试，并核对公开构建/打包门槛；全部使用 fixture，不调用模型。前端显示生成时间、原句和缺项；维护抽查中文语义仍需人工回查。模型尝试独立软阈值 `MODEL_CALL_CAP` 默认300/UTC日，失败及验证重试计数不退款；KV不是原子费用封顶。细节见 [AI服务说明](AI解读部署说明.md)。

- 每天：查看 Actions、last-refresh 和 deployment-status；区分刷新、Pages、state 保存及 optional 失败。查新超过 6 小时或源健康过期要排查；零输出须结合 rawItems/eligibleItems，不能直接认定故障。
- 每周：检查反复失败源、PubMed truncated 计数、速览覆盖、待核对稿与全文进度；查看 Actions 用量、Cloudflare Worker 错误、KV 和 AI 配额。Actions 绿色不证明 AI 成功。
- 每月及凭据到期前：平台核实 Actions 额度、Pages 自定义域名/TLS、KV 绑定和最小权限令牌期限。只记录配置名称及有效/缺失状态，不读取或粘贴凭据值。
- 发布后：核对 Pages 步骤、源码 SHA、manifest 六文件和部署状态；公网可用时核对站点版本、摘要、速览标签、分页和原文链接。网络受限写“Pages 已接受，公网未独立验收”，不称宕机或完整验收。

最终证据作为私有 `pipeline-final-<run id>-<attempt>` Actions artifact 上传，失败也保留。state 中部署快照表示 Pages 已接受、state 写入尚待完成；最后的 artifact 记录实际 state outcome。保存由 `scripts/save_state.py` 执行，使用恢复时固定 SHA（或本次最后确认的检查点 SHA）的 force-with-lease，拒绝覆盖未观察到的并发 state。若租约被拒且远端新增提交全部是本次运行的检查点提交（只改检查点文件），则合并这些文件后以新租约重推一次；其他写入者仍失败。这覆盖“检查点在 GitHub 已生效但客户端超时”的情形（2026-10-10 运行 38010683523）。fast 无内容变化时报告留 artifact、state 不推进，下轮仍从最近成功发布恢复。

Cloudflare runtime 与 Actions 模型配置分别管理。静态发布成功不能证明 runtime KV、AI 开关、额度或模型连通性正常。不要为验证付费调用模型或下载 PDF；平台只读状态和获授权实际运行是证据。

官方依据：[GitHub 工作流触发规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Cloudflare CI Direct Upload](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/)。
