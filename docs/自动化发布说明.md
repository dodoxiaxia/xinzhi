# 网站运营与发布（v13.6）

执行端是 GitHub Actions，公开站点是 Cloudflare Pages `dryz-xinzhi` / https://learn.dryz.info/。`main` 保存代码和人工核对稿，私有 `state` 保存抓取数据、摘要缓存和最近成功发布的六文件。Macmini 是私有文献归档目标，网站发布不依赖它运行。AI- 原文下载与归档是另一条流程。

## 更新频率与内容边界

| 工作 | 频率（北京时间） | 完成标准 |
|---|---|---|
| RSS/PubMed 查新、当前源健康、规则精选 | 每 2 小时 :07，GitHub 可能延迟 | 本轮获取状态、近 14 天候选、内容变更时发布 |
| 365 天存档、摘要补全、标题翻译、AI 速览 | 每天 05:17 | 总时间预算内执行；结果和跳过原因留报告 |
| 代码、页面、人工稿发布 | main 相关路径更新时 | 轻量查新与构建通过门槛并由 Pages 接受 |
| 摘要核对导读 | 新稿完成来源核对后 | 证据范围、来源 URL、published 日期；published=false 不公开 |
| 全文精读 | 每周选题与审查，取得全文后发布 | 完成全文审查；未完成显示尚未发布，不把旧期改日期 |

自动聚合、规则精选、AI 速览不等于人工核对或全文精读。公开文献库是既有 1,219 条题录范围；私有 AI- 索引增长不自动扩大公开范围。页面分别展示查新、导读和速览时间。

## 唯一发布入口

`.github/workflows/daily.yml` 保留已有两条 GitHub cron，不新建第三条调度。手动 full 可直接运行；手动 fast 须勾选 `allow_fast_dispatch`。原 Cloudflare Cron Worker 只传 mode=fast 的重复请求在 GitHub 入口被忽略；这不代表 Cloudflare Cron 已停用。账户可访问时应停用旧 Cron 并撤销不再使用的专用令牌。

固定 state 恢复 → RSS/PubMed → 合并 → 轻量精选；每天和人工 full 再做存档/补摘要/翻译/速览 → 白名单构建 → 门槛 → Pages → 成功后才写 state。main 源码更新使用 fast，避免小改动重复调用模型；fast 不调用模型或大存档。六个公开文件都进入内容比较；刷新时间变化不重新发布。full 总预算 50 分钟、fast 25 分钟，给模型和构建留时间；Actions 硬上限 60 分钟。可选步骤失败/超时/预算跳过如实记录。

public 必须恰好 index.html、public.js、style.css、icon.svg、_headers、_worker.js；雷达至少 300、文献库至少 1,000。摘要缓存缺失、既有导读丢失、公开私有路径或多余文件均停止构建。AI 单篇不通过证据校验则跳过，合法输出可保留；模型鉴权/限流/传输故障停止后续请求并保留旧缓存。诊断只含白名单元数据，不存响应或凭据。

## 定期运维和故障处理

每次既有定时刷新和相关 main 更新先调用 `ci.yml` 的只读质量门禁；PR 和手动检查也使用同一门禁。只恢复固定 state 的 data/public，不加载生产模型密钥，执行全量离线回归与真实数据白名单构建。质量失败阻断刷新并保留 quality artifact；刷新 job 开始后，最终报告和公网检查保留在 pipeline-final artifact。未确认的旧 fast dispatch 使用独立并发组，避免挤掉合法 pending 刷新。

发布前保存上一成功 state 的六文件、manifest 和 SHA 为 previous-release artifact，保留 30 天；发布后只读检查首页、运行配置和当轮发布的四个 HTTP 静态文件哈希。检查不生成模型回答、不下载文献。网络阻断记 unverified，配置缺失、近期提供商故障或资产差异记 degraded；AI 主动关闭单独记 generation_disabled。公网冒烟失败会使本轮 Actions 失败，已接受的部署和 state 结果仍分别保留，不自动回滚。

`deployment-status.json` 的 `deployed` 仍表示 Pages 接受事实；新增 `pipelineStatus`、来源成功/失败计数和固定 warning，识别可选步骤失败/预算跳过及 state 保存不完整。state 中的 pending 快照应结合对应运行的最终 artifact 判断。完整风险和回滚步骤见 [复杂度与运维风险评估](复杂度与运维风险评估.md)。每日心知运维巡检已启用，只在新故障、明显变化或需要处理时通知；发布仍使用已有两条 GitHub cron。

v13.6 公开摘要研究结构/逐篇对照沿用现有 Pages KV 与模型配置，不新建调度。每次实际部署前执行 Worker、阅读逻辑、研究服务及 UI 的离线 Node 测试，并核对公开构建/打包门槛；全部使用 fixture，不调用模型。前端显示生成时间、原句和缺项；维护抽查中文语义仍需人工回查。模型尝试独立软阈值 `MODEL_CALL_CAP` 默认300/UTC日，失败及验证重试计数不退款；KV不是原子费用封顶。细节见 [AI服务说明](AI解读部署说明.md)。

- 每天：查看 Actions、last-refresh 和 deployment-status；区分刷新、Pages、state 保存及 optional 失败。查新超过 6 小时或源健康过期要排查；零输出须结合 rawItems/eligibleItems，不能直接认定故障。
- 每周：检查反复失败源、PubMed truncated 计数、速览覆盖、待核对稿与全文进度；查看 Actions 用量、Cloudflare Worker 错误、KV 和 AI 配额。Actions 绿色不证明 AI 成功。
- 每月及凭据到期前：平台核实 Actions 额度、Pages 自定义域名/TLS、KV 绑定和最小权限令牌期限。只记录配置名称及有效/缺失状态，不读取或粘贴凭据值。
- 发布后：核对 Pages 步骤、源码 SHA、manifest 六文件和部署状态；公网可用时核对站点版本、摘要、速览标签、分页和原文链接。网络受限写“Pages 已接受，公网未独立验收”，不称宕机或完整验收。

最终证据作为私有 `pipeline-final-<run id>-<attempt>` Actions artifact 上传，失败也保留。state 中部署快照表示 Pages 已接受、state 写入尚待完成；最后的 artifact 记录实际 state outcome。保存使用恢复时固定 SHA 的 force-with-lease，拒绝覆盖未观察到的并发 state。fast 无内容变化时报告留 artifact、state 不推进，下轮仍从最近成功发布恢复。

Cloudflare runtime 与 Actions 模型配置分别管理。静态发布成功不能证明 runtime KV、AI 开关、额度或模型连通性正常。不要为验证付费调用模型或下载 PDF；平台只读状态和获授权实际运行是证据。

官方依据：[GitHub 工作流触发规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Cloudflare CI Direct Upload](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/)。
