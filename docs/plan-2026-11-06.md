## 1. 匿名读者只读已审缓存，只有登录的维护者能触发生成

现状。打开页面不会生成。近7天榜每一行的 `allowAutomaticGeneration` 固定为 false，`scripts/ci_daily.py` 里的发布策略也把 `automaticGenerationOnPageLoad` 写成 false，若某一行允许打开页面就生成，构建会失败。`GET /api/ql` 和 `GET /api/ai` 把 KV 里已经存下的结果返回给任何访问者。`POST /api/ql` 和 `POST /api/ai` 在 `canGenerate(env)` 为真时直接调用模型。这个判断只看 `QL_KV`、模型密钥、端点和 `AI_ENABLED`，不看是谁在请求（`edge/src/07-ai-tasks.js`、`edge/src/08-router.js`）。现在的“维护者”是浏览器标志：访问 `?maintainer=1` 会写入 `localStorage` 的 `xz_maintainer` 和同名 cookie，用来显示汉堡菜单和 PDF 入口（`src/app/01-state-helpers.js`、`edge/src/00-header-pdf.js`）。这不是登录账号。已经公开的 AI 内容标注为未经人工核对，缓存上的审核状态是机器校验，不是人工终审。定时任务 `week_precompute`、`generate_quicklooks`、`translate_titles`、`daily_fulltext` 在没有登录用户的情况下生成。

做法。匿名响应只返回已经入库、并且明确允许公开的缓存。触发生成的 POST 改为要求真正的维护者凭据，不再接受查询参数标志。定时预生成与读者在页面上点生成要分开：前者仍由现有调度运行，后者只对登录维护者开放。

工作范围。改动集中在边缘路由的鉴权、缓存条目的公开标记，以及前端生成按钮。密钥仍只放在 Cloudflare 和 GitHub 的 Secret 里。

风险。若把现有 KV 一律对匿名读者关闭，每日精选和近7天榜上已经展示的机器译文会一起消失。把 cookie 标志当成登录，等于任何人打开 `?maintainer=1` 就能生成并计费。

未决。Donald 决定匿名读者看到的“已审”是机器校验、人工核对，还是另一条临床标准。定时预生成算不算维护者操作，也要在那之后再定。

## 2. 按字段对账，一个坏字段不丢掉整篇

现状。`configured_batch` 已经会留下校验通过的兄弟字段，把该次请求标成 `rejected` 并记下 `taskFailures`，然后只重试失败的字段（`MAX_TASK_REJECTIONS` 为 2）。传输失败或检查点写失败仍然暂停这次请求带上的全部任务。这次代码改动把新的暂停拆成翻译、研究结构、速览三个标志，但一次合并调用同时列出三项时，检查点失败仍会把三项一起暂停。2026-10-24 那次请求就是一次合并调用，三个字段的答案都没有进入缓存。处于不确定状态的合并请求会挡住这些任务，直到有人按规则对账。这次提交的对账工具在缓存不齐时拒绝，因为那一次调用只记了一笔费用，缺的字段再生成会再计一次。按字段保留内容还没有实现。

做法。每个字段一通过校验就单独写入缓存，并在同一条请求上记下字段级结果。研究结构失败时保留已经通过的翻译和速览。已经在缓存里的字段不再发给模型。

工作范围。改动在 `scripts/week_precompute.py` 的合并调用落盘顺序、账本上的字段级结果，以及对账工具对“只缺一部分字段”的处理。

风险。一次已经计费的合并调用若被拆开、缺的字段再生成，缺的那部分会再计一次费。答案如果根本没有落盘，按字段也没有内容可以复用。

未决。缓存只齐一部分时，缺的字段是继续暂停，还是等维护者明确同意后再单独生成。

## 4. 每日监测增加周榜覆盖、校验失败率和全文精读完成数

现状。`scripts/ci_daily.py` 已经算出 `weeklyContent`：状态、入选篇数、题名与翻译、研究结构、速览的覆盖、完全齐备篇数、待补篇数，以及 `generationStep` 的结果和退出码。全文精读完成情况来自 `daily_fulltext.public_readings`，写入 `deepReadings`。这些数字会打印成 `WEEKLY CONTENT`，存在 `docs/last-refresh.json`，并随流水线产物上传。它不算校验失败率，也不通知任何人。`week_precompute` 是可选步骤，所以轻量刷新可以在预生成暂停时仍然成功。2026-11-06 的产物里周榜状态是 partial，覆盖是题名 24、翻译 0、研究结构 0、速览 0，生成步骤失败且退出码为 1，流水线状态仍是 success。

做法。每次运行在 `last-refresh.json` 旁边再写一份异常摘要，只设计这份 JSON，不发送。字段为：

- `weeklySelected`：入选篇数。
- `coverage`：题名、翻译、研究结构、速览各自的篇数。
- `pendingFraction`：待补篇数除以入选篇数。
- `generationBlocker`：生成步骤的结果、退出码，以及账本上的暂停原因。
- `validation`：当天账本里 `rejected` 与 `validated` 的次数，以及 `taskFailures` 的条数，用来算失败率。
- `deepReadings`：`day`、`target`、`completed`、`state`。
- `summary`：一句中文，列出覆盖低于阈值、生成被挡住、校验失败率高于阈值、全文精读完成数低于目标。

去向是内部协调人。本文不接 Slack、邮件或其他渠道。

风险。可选步骤失败不让整条流水线失败，这是现有设计。摘要如果只在流水线失败时才写，像现在这种“流水线成功、周榜全空”会被漏掉。阈值写死，会在榜单本来就短的日子误报。

未决。各项阈值、谁来看这份摘要，以及暂停的可选步骤要不要改成让整条流水线失败。
