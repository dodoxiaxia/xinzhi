## 最小补丁与契约

`scripts/editorial_review.py` 校验具体稿件版本、医生批准及单独发布请求。`scripts/prepare_editorial_handoff.py` 只在本 checkout 的私有暂存目录生成交付与审计摘要，不写 editorial、main、state，也不联网、触发 Actions 或部署。

`scripts/build_public.py` 对新导读采用该门禁，并在候选/文献库中以 main 的当前审核决定覆盖 state 旧 draftData，阻止待审或撤回内容从旧缓存漏出。正文进入公开白名单前剔除审核人、review/publication、全文材料和审计身份。

12 篇历史导读使用 `editorial/legacy_published_guides.json` 的固定正文指纹与原日期保留公开历史。该表只登记已证实公开的 12 篇，**不应把新稿追加进去来绕过终审**。已有稿未审改动或改日期会阻止构建；已发表稿被待审新版本替换也阻止构建，保留原生产。明确 `published=false` 或撤回状态才允许从公开归档排除。

新增稿的 `source_checked=true`、`prepared_on` 或单独 `published` 字段均不授予公开权限。医生批准后没有独立发布请求仍私有。审核/发布指纹不匹配、缺必要字段、错误日期或伪装全文均阻止入库。

审核事件形状如下。此处为契约示意，空占位符不是实际审核记录：

```json
{
  "review": {
    "schema_version": 1,
    "state": "awaiting_physician",
    "content_sha256": "<对规范化稿件身份、正文和证据范围计算的SHA256>",
    "reviewer_id": "<可信身份服务提供>",
    "reviewer_role": "physician",
    "decided_at": "<带时区的真实终审时间>",
    "event_id": "<私有审计事件ID>"
  },
  "publication": {
    "schema_version": 1,
    "state": "not_requested",
    "content_sha256": "<同一稿件SHA256>",
    "review_event_id": "<对应批准事件ID>",
    "event_id": "<不同的私有发布请求事件ID>",
    "requested_by": "<最终集成人身份>",
    "requested_at": "<带时区的真实发布交接时间>",
    "published_on": "<交接当天北京时间日期>"
  },
  "published": false
}
```

只有 review.state 为 `approved`、publication.state 为 `release_requested`、顶层 published 与发布请求日期相同且两个事件均有效时，新稿才有构建资格。状态拒绝/撤回或显式 false 仍不可见。重复事件、未来事件、无时区事件和审后改稿均拒绝。

指纹由 `content_sha256(draft, article_key(draft))` 计算，采用排序 JSON 和 UTF-8；包括题名、导读、局限性、学习问题、研究类型、依据、来源、归属声明等全部公开正文。若为 weekly，还包括原目标周、全文正文、证据表与原文文件 SHA。有 DOI 的稿件使用规范化 DOI 为身份；无 DOI 的稿件使用与候选匹配的稳定 ID。

全文交付另需 `content_kind=weekly`、`evidence_basis=fulltext`、`target_week.start/end`（周一至周日）、`body_markdown`、`evidence_table_markdown` 和 64 位 `source_document_sha256`。契约校验存在性/版本身份，不检查医学内容是否正确，也不证明 PDF 已读。

**权限边界：这些字段的结构校验不能认证填写者。** 可信医生会话、服务器审计写入、乐观版本检查和身份核验仍须由原任务/后续审核服务实现。不要将客户端自报的 physician 角色直接作为可信批准，也不要把 CLI 成功称作医学审查或生产闭环已完成。

当前网页仍沿用“摘要核对、未经医生终审”的历史标签；本补丁不增加公开“医生已审”承诺。最终产品接线需在证据边界明确后准确展示新稿审核范围，并继续区分摘要导读与全文精读。
